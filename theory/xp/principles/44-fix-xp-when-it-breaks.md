# Fix XP when it breaks

**Rule:** Start by following the rules, but change what does not work through retrospective meetings, and make improving the process a routine part of development.

**Why:** The author says it is a when, not an if, that changes will be needed. The rules still bind until the team changes them, since developers must know exactly what to expect from each other. The rules are not the goal: they set expectations to build a collaborative, empowering environment, and teamwork continues as rules change. Add your own values by changing the rules.

**Do:**
```
follow the rules as written first
retrospective: what works, what does not
agree the change as a team, announce it, then follow the new rule
```

**Don't:** Dropping rules whenever individuals feel like it.

**Break it when:** The site's whole point is that the team may change any rule once it has agreed.
