# A proposal needs a problem, a budget and a solution

**Rule:** Consider a proposal only when it holds one concrete problem story, a time budget and a rough solution; circulate it in writing and collect comments that add information.

**Why:** A solution with no problem has no fitness test, so debate becomes taste. A problem with no solution is unshaped. A stated budget turns reviewers into partners in finding a simple idea. Separating the problem lets "is the demand real?" be argued apart from "is the solution good?". Written, asynchronous review spares people's time and keeps the decision meeting short.

**Do:**
```
proposal = { problem: story, budget: N, solution: parts + connections,
             rabbit_holes: patches, no_gos: fences }
reject if problem, budget or solution is missing
post it; comments = holes and missing facts, not votes
```

**Don't:** Pitch "add tabs" or "make messages easier to find", or read the document aloud in a meeting.

**Break it when:** Everyone shares the context; shorten the problem to a line but keep it.
