# Plan in fixed cycles with a cool-down between them

**Rule:** Use a standard cycle long enough to finish a whole meaningful project and short enough that the end is felt from day one, followed by a short period with no scheduled work.

**Why:** Overlapping variable-length projects turn scheduling into a puzzle; very short sprints spend too much on planning for what they produce; a distant deadline lets teams drift. The end of a cycle is the worst moment to plan because everyone is finishing, and free time lets people fix long-standing bugs and try technical ideas.

**Do:**
```
cycle    = 6 weeks fixed ; projects shaped to fit one cycle (or small batches inside it)
cooldown = 2 weeks      ; decide next bets, builders choose their own work
capacity = number of standard teams
```

**Don't:** Run cycles back to back so planning happens in the crunch, or plan open-ended projects.

**Break it when:** Tiny teams or operational work can use another length if both properties hold: a whole project fits, and the end is visible. A real crisis can still use the cool-down.
